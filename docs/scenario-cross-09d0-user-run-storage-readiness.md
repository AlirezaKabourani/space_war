## What actually remains after refresh / browser restart / switching users

S1: a successful completed run writes `space-war.scenario4.redesigned-s1.final.snapshot`, containing full cognitiveScoresV3 with nulls and version stamps. The key is unscoped and overwritten on each completion. It survives normal same-origin reload/browser restart, subject to storage retention. On mount the code reads ONLY `space-war.scenario4.redesigned-s1.run` to reuse runId/seedBase and creates a NEW initial state with phase intro_title; snapshots/decisions/finalSnapshot initialize null/empty. It does not load the final snapshot into the dashboard. A stored snapshot is evidence of a last-written global completed object, not proof of the current user's latest run. Switching users does not clear/rekey that snapshot/run token. No run ID reset was found.

S2: full runtime/result are in memory only, but completion event detail.cognitive is retained in the analytics localStorage array if logging was enabled and persistence succeeded. This contradicts an overly broad “S2 has no persistent cognitive data” reading; the accurate distinction is “no runtime/report rehydration, but full completion-result JSON can persist in logs.” eventLogger.getEvents can read those bytes after restart/switch. There is no implemented nested-cognitive selection, validation, ownership gate, latest-run rule or report reconstruction function. When Summary props are missing/mismatched, it renders unavailable; it does not fetch a previous result or convert missing data to 0. A new actual run assignment is generated at start, rather than restoring a saved runtime.

Runtime timing fields in S2 originate from performance.now when available, otherwise Date.now (`presentation.ts`, monotonicNow); an isolated completedAtMs does not identify an absolute completed timestamp. The completion event's ts is the actual available calendar log timestamp. Its scientific payload omits runtime completedAtMs. Do not equate runId's epoch-start fragment or event timestamp with a canonical completedAt field.

No real user's installed storage was inspected. Therefore the number of real S1/S2 snapshots currently available on this machine is NOT DETERMINABLE. This does not mean zero runs. ## App analytics is not a scientific result store

`renderAdminAnalytics` (`App.tsx:1278`) requires activeProfile.role=admin and reads eventLogger.getEvents. Selected user defaults to "all"; event filtering is exact userId only when a specific user is selected (1292-1297). General buildInsights/buildCognitiveInsights calculate event/quiz heuristics; they do not retrieve either canonical cognitive V3 object. The legacy S1 analysis branch explicitly targets `s1_shadows_low_orbit` (`App.tsx:1398`), not released id=4.

buildScenarioRuns (1298-1335) sorts by ts, counts attempts per scenario string and creates synthetic `sid::attempt`. Its openRuns key is ONLY scenario ID, so the default all-users view can mix user start/end boundaries. It closes on scenario_end OR scenario_exit, drops open unfinished runs from the resulting list, and sorts completed/closed entries by descending start. Selected run defaults to "all"; an unmatched selected ID falls back to all user-scoped events (1336-1345). There is no automatic latest scientific run selection. Time-window filtering for an analytics run is not scientific run linkage.

getUserAnalytics groups by `userId::userName` (`App.tsx:539-542`); a changed display name can split summaries for one ID. Completion events with missing userId are not safely assigned by name. Neither `sid::attempt`, display name, timestamps alone, profile progress, event UUID, world ID nor seed is a substitute for canonical scientific runId plus proven ownership.

S1 canonical-looking `run-${Date.now()}` is generated only if the global RUN_KEY is absent; it is reused. seedBase embeds the first mounting profile string while later rngSeed includes current profile id, so seedBase is not reliable owner metadata. S2 assignmentKey is profile-or-anonymous|epoch|s5-v3; worldHash/seedHash use fnv1a32; runId=`s5-${epochStartedAt}-${worldHashHex8}` (`ui/runAssignment.ts:23-34`). That is a client-generated assignment ID, not an authenticated owner token; anonymous runs and same-time/hash reuse are possible. No run merging was attempted.
